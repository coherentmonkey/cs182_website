Report: Using Claude 4.5 Haiku as a Coding Co‑Pilot for the SSM GPU Homework Executive Summary For this special participation assignment (Part B), I used a single modern LLM—Claude 4.5 Haiku (thinking)—to tackle the coding portions of the CS282 SSM homework 8. I did not mix models: the code edits and homework‑related documentation under special_participation_B/HW8_code were produced with Haiku 4.5, with me steering, testing, and sometimes overriding it. I had it working on the code in q_coding_ssm_forward_cpu.py, q_coding_ssm_forward_gpu.py, and their associated notebooks and tests. I logged the interactions in conversations/CodingSSM_CPU.md and conversations/CodingSSM_GPU.md. Two constraints I imposed: I would only use Haiku 4.5 for all problems. If the model could not reach a correct derivation on its own, I treated that as a failure of “autonomous solving,” even if I later patched the code. My findings were: CPU part: Haiku 4.5 did reasonably well. With some prompting and shape debugging, it produced correct recurrent and convolutional SSM forward passes, plus consistent complexity analyses and written answers. Its mistakes were mostly ordinary implementation bugs, not conceptual failures. GPU part: Haiku 4.5 could not independently produce correct GPU convolution implementations of the SSM, either in the general or diagonal case. The core failures were around how it set up the convolution relative to the SSM formula (kernel contents, time indexing, and channel interaction), not the idea of using a convolution itself. Hallucinations and drift: Once Haiku had written a wrong‑but‑plausible solution, it tended to bring that pattern back later. It also wrote confident documentation and performance claims that did not always match the actual implementation. Overall, Haiku 4.5 was a useful assistant for boilerplate, explanations, and CPU code, but it could not autonomously solve the GPU portion of Part B. I had to drag it to the final answers using tests, benchmarks, and my own understanding of the SSM math. Methodology I worked in Cursor with Claude 4.5 Haiku (thinking) as the agent. Code lived in special_participation_B/HW8_code/. After each model edit, I ran the code and pasted errors back into the conversation, then asked Haiku to debug. This process let me separate what the model could do on its own from what required active human steering. CPU Coding Journey On the CPU side, Haiku performed as a competent co‑pilot. Recurrent SSM (unrolled_ssm_forward): The first non‑trivial attempt was essentially correct. It unrolled ht+1​=Wht​+Uxt​+b, maintained a running hidden state h_t, and stored the sequence in h_all with shape (N, T, H). Only minor shape/broadcasting checks were needed, and sanity_check() showed agreement with the spec. Convolution kernel and forward pass (make_conv_kernel, conv_ssm_forward): Haiku correctly recognized that the kernel should store powers Wk and used a binary‑exponentiation style routine to build them efficiently. For the forward pass, it implemented h[:,:,t]=∑k=0t​s[:,:,t−k]@(Wk)T using nested loops. After a short debugging phase about matrix multiplication order, sanity_check() showed max differences ~10−8 vs. the recurrent implementation. Word questions (Q1–Q5): The model produced answers that matched both the math and the CPU benchmarks (e.g., recurrent O(NTH2), convolution O(NHT2+H3logT), and why recurrence wins on CPU for large T). These are reflected in SOLUTIONS_CPU.md and the CPU notebook. On the CPU side, the model both implemented and explained the solutions with modest prompting. GPU Coding Journey The GPU portion exposed more serious limitations. Recurrent Code on GPU Porting unrolled_ssm_forward to GPU (changing the default device and reusing the CPU logic) worked smoothly. The recurrent GPU code is essentially identical to the CPU version and passes sanity_check(). Convolution Attempts and Their Failure For the convolution‑based GPU implementations, the model’s first instinct was to express the SSM as a convolution over time. However, it repeatedly mis‑specified the convolution: It built kernels and applied them in ways that did not correspond exactly to ht​=∑k=0t​Wkst−k​. It did not consistently handle the required time reversal and indexing. It treated per‑channel elementwise accumulation as if it were the same as the matrix multiplication Wk@st−k​. As documented in BUG_FIX_REPORT.md and UPDATED_ANALYSIS.txt, these versions produced max differences around 0.345 vs. the reference, despite the model’s explanations claiming they were equivalent. Returning to Literal SSM Formulas The final, correct GPU implementations in special_participation_B/HW8_code/q_coding_ssm_forward_gpu.py match the literal SSM formulas and use explicit loops: conv_ssm_forward now computes h[:,:,t]=∑k=0t​s[:,:,t−k]@(Wk)T in a nested Python loop over t and k. diag_conv_ssm_forward uses the diagonal powers w_i^k from make_diag_depthwise_kernel and computes hi​(t)=∑k=0t​wik​⋅si​(t−k) with explicit loops. These versions pass both sanity_check() and diag_sanity_check() with max differences on the order of 10−8, and UPDATED_ANALYSIS.txt confirms their mathematical correctness. Crucially, they only emerged once I stopped asking the model to “optimize” the convolution and instead forced it to implement the formulas directly, even if that meant slower Python loops. Benchmarks and Answer 6/7 GPU benchmarks for H=512,N=512 (see UPDATED_ANALYSIS.txt) showed: Unrolled recurrent time ~0.034 s, almost flat as T increases from 32 to 512. Convolution time exploding from ~0.001 s (T=8) to ~10 s (T=512), dominated by Python loop overhead, not by raw FLOPs. I used these numbers to have Haiku rewrite Answer 6 in the GPU notebook and ANSWERS_GPU.md. The final answer correctly explains that: The recurrent path runs through optimized GPU matmuls and benefits from batching and cache locality. The convolution path (in this implementation) is throttled by nested Python loops calling into the GPU, so implementation details dominate theoretical complexity. Hallucinations and Drift Across the GPU work, two consistent issues appeared: Narrative over‑reach: Some documentation files describe the GPU implementations as “highly optimized” or “production‑ready” in ways that don’t fully match the Python‑loop reality. Drift: After fixing the code to use nested loops, later documentation passes sometimes still talked about earlier, incorrect convolution setups as if they were still relevant. Lessons Learned Tests and sanity checks are essential. Without sanity_check(), diag_sanity_check(), and the GPU benchmarks in UPDATED_ANALYSIS.txt, the incorrect convolution setups and the “GPU optimized” narrative would have been easy to mindlessly accept. Wrong patterns stick. Once a flawed pattern (like a mis‑specified convolution) is in the context, the model tends to reuse it unless you actively push it away from that idea. For math‑heavy GPU code, the model is better as an explainer than as a designer. It can derive complexity tables and explain why diagonal structure helps, but it struggles to design GPU implementations that work efficiently. Conclusion For Part B—using an LLM/co‑pilot on the coding parts—the outcome was mixed: On the CPU side, Claude 4.5 Haiku was a capable assistant: it implemented the core functions, produced correct explanations, and only needed modest debugging help. On the GPU side, it could not independently reach correct convolution‑based or diagonal GPU implementations under the constraints of my experiment. Those only became correct when I gave it the correct answer. Even then, its code was bottlenecked by the Python loop overhead and could not match the performance of the correct implementation. As a result, I consider Haiku 4.5 a helpful co‑pilot but not an autonomous solver for this GPU coding task. Getting fully correct solutions required me to already know what “right” looked like, to steer the model there, and to keep it from drifting back toward attractive but wrong abstractions—exactly the sort of “dragging” behavior the assignment prompt anticipated for this kind of experiment.
