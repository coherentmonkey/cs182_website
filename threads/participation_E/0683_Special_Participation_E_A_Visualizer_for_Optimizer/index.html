Special Participation E: A Visualizer for Optimizers

By Kithmini Herath 2025-12-08 Claude
View on Ed Stem →
Hi all, I created an optimizer visualization tool (https://kithminiherath.github.io/optimizer-vis/) to interactively analyze how different hyperparameters affect the loss minimization trajectory for the following optimizers: AdamW SGD (with and without nestorov momentum) Muon To build this visualizer I used classic optimizer test functions (2D loss landscapes) to test convergence, precision, robustness and performance of the above optimization algorithms: Sphere Gaussian Bowl Rosenbrock Rastrigin The code for this visualizer is available at: https://github.com/KithminiHerath/optimizer-vis which can be used to extend to more optimizers. This visualization tool was built with the help of Gemini 3 on Antigravity using TypeScript and three.js. I also used Claude Code as a secondary agent to get a different view of the code implementations by Gemini and to weed out implementation bugs. For a lightweight webapp deployment all optimizers and loss functions were implemented with TypeScript. To ensure there were no implementation bugs, I ran test benches comparing the TypeScript optimizers' step-wise outputs for loss functions against the corresponding PyTorch libraries. How I built the visualizer to represent Muon on 2D loss landscapes: Implementing AdamW and SGD were quite straightforward, but it was challenging for me to make this visualizer to work for Muon in a meaningful way. This is because Muon only works for 2D parameters and the loss functions and the rest of this visualizer was built for vectors. Chatting with Gemini 3 we came up with the following workflow to make this visualizer work for Muon as well in a meaningful way: Since Muon needs 2D parameters we defined a “matrix mode” where a parameter matrix was defined as $$W=\left[\begin{matrix}x&z\\y&w\end{matrix}\right]$$ In the Muon implementation the rows will be orthogonalized here. We define the “visible parameters” as $x$ and $y$ and the remaining parameters as “dummy” parameters. By separating $x$ and $y$ into different rows, you force the optimizer to make them orthogonal. If they were in the same row, they would just be normalized together. Even if $z$ and $w$ are dummy parameters we still need to define gradients for them. Therefore we don’t fix them, in-order for them to support the orthogonality constraints and also to prevent the matrix from being rank-1. Currently they are initialized to -1 and 1 and the final loss function is defined as: . $$L_{total}=L_{2D}\left(x,y\right)+z^2+w^2$$ $L_{2D}(x,y)$ is one of the four previously mentioned 2D loss functions and the remaining terms follow a simple bowl objective. Providing a "slope" for the hidden dimensions this way ensures the matrix has sufficient rank for the Newton-Schulz iteration to work non-trivially. Under the above loss function the weights are optimized with the standard Muon implementation in TypeScript and we only visualize the behavior of $L_{2D}(x,y)$ in the tool. I think this is still a mathematically valid way to observe the behavior of Muon in comparison to the other two optimizers. I also want to note that when Muon is selected as an optimizer from the controls in the visualizer, any other optimizer selected with it will also be working on matrix parameters for common ground. Features of the visualizer: 2D contour and 3D surface plots for visual representation of the loss landscapes. This way during a run the user can analyze both views. I think the 3D view is especially useful when there are multiple local minima, saddle points and when it’s not apparent on the 2D contour plot why the optimizer got stuck at certain points. Loss function control – select any loss function. Configure Optimizer panel – Type – optimizer type selection Hyperparameter sliders to configure the optimizer and add it. You’re able to select multiple optimizers at different configurations during a run and they will be listed with the choices of hyperparameters in the Optimizer List. You can also set the starting points of $x$ and $y$ by either clicking anywhere on the contour plot or typing out coordinates in the "start X" and "start Y" boxes. You can also set the number of maximum steps you want the optimizer to run for. The default is 200 steps. You start the run with “Start” button and it’ll automatically run until it hits the maximum number of steps. You can also pause runs or step through iterations one step at a time with the “Step” button. While the “Stop” button resets to the beginning of the run, the “Reset” button resets the visualizer. Some cool visualization examples: Learning rate comparison within the same optimizer type: AdamW with higher learning rate converging faster by escaping local minima: Comparing several optimizers: AdamW finds the global minima but both SGD versions reach the local minima: Muon originally moves towards the local minima but is able to recover and change the trajectory towards the global minima. I think this shows how Muon’s orthogonality constraints initially causes the dominant gradient at that point ($dy$) to affect the gradients in other directions and may overall pull in the local minima direction, but I think once $dw$ and $dz$ recovers under their loss it snaps back in the direction of the global minima: Muon seems to do great in converging at more complex loss landscapes. I think this is an interesting case that shows how Muon’s spectral norm constraints essentially “saves” it from exploding gradients along steep valleys and take controlled steps and eventually reach the global minima efficiently while the other optimizers seem to be distracted by the steep gradient in one direction (wall like structure) and gets stuck at local minimas since the gradient in other directions (valley like structure) gives less of a signal to move: Limitations: Users are unable to see the behavior of the hidden parameters in the matrix mode. Users cannot set different values for the hidden parameters and analyze how that affects optimization trajectory of the 2D losses. I think this is a useful tool for anyone trying to understand how certain hyperparameters affect certain loss functions, gain insights into the behavior of different optimizers even if it’s for relatively simple loss landscapes. I think it would be a good playground to test specific instances to understand optimizers for academic purposes. Hope y’all can also check this out and let me know if you have any feedback. I’m also interested in expanding this to other optimizers in the future.
